Capture the work just completed in this session as a reusable Alis Build skill for my team — like recording a macro after doing the steps by hand: generalize the steps, not the session. (1) Dedupe first: run `alis skills search "<what the work accomplished>" --json`; on a close match do NOT create a near-duplicate — offer instead to load the existing skill (`alis skills load <id>`), improve it if I own it (`alis skills edit <id>`), or send feedback to its owner (`alis skills feedback <id>`). (2) Confirm scope once: propose a lowercase-hyphen skill id and a one-line description, and ask ONE confirmation covering both the id and what the skill should and should not cover; do not iterate on naming before registering. (3) Register the draft: `alis skills capture <id> --name "<Display Name>" --description "<description>" --json` (fall back to `alis skills create` with the same flags if the capture subcommand is unavailable); this reserves the draft in the registry and returns the workspace path. (4) Distill into the workspace: write generalized, reusable steps with decision points and verification steps — not a session log; parameterize specifics like `<project-id>`, `<service>`, `<org>`; scrub absolute/home paths, emails, org/project ids, tokens/keys, and internal URLs; make the description's first clause say what the skill does, then "Use when …" with trigger phrases (it is both the harness trigger and the search-ranking surface); optionally add `references/` files for a scrubbed worked example. (5) Write the eval while ground truth is fresh: fill `evals/cases.yaml` with 1-2 cases whose prompt is a generalized version of the task just done. (6) Review in-session: show me the frontmatter description and the step headings (not the whole file) and iterate on my comments; mention that the workspace persists at `~/.alis/skills/workspaces/<id>/` and can be continued later via `alis skills open <id>`. (7) Publish only on my explicit approval: `alis skills publish <id>`. (8) After publish, offer once: `alis skills evaluate <id>` (recommended before team-wide sharing) and `alis skills share <id> --domain` (whole team) or `--email <addr>` (individual) — my team will find it by just describing the problem; discovery surfaces it automatically.
